# 턴별 모델 전환 검증 계획

## 1. 연결·무결성

1. `pass`로 같은 요청이 기본 Codex와 동일하게 완료되는지 확인한다.
2. `force`로 다른 모델을 선택한 뒤 응답과 도구 연속 요청이 모두 같은 모델로 가는지 확인한다.
3. SSE 출력, HTTP 상태·헤더, 모델 목록, 명시적 수동 모델 지정이 원래대로 동작하는지 확인한다.
4. 서버 종료·Jev 오류·타임아웃에서 비밀이나 프롬프트가 로그에 남지 않고 안전하게 실패하는지 확인한다.

현재: 2026-09-25 기준 자동화 테스트 67개와 타입 검사 통과(Node.js 25.8.1). 기존 Codex CLI `pass`와 `force(gpt-6-luna)` 실호출 성공 기록은 유지했다. Codex CLI와 Claude CLI의 합성 관찰 턴, Claude 데스크톱 Code 탭의 Jev 추천·앱 응답 턴, 실제 Jev를 사용한 Codex CLI 연속 자동 전환을 완료했다. Codex 데스크톱에서도 수정된 라우터로 실제 Jev `shadow` 추천과 제한적 `auto` 전환을 각각 확인했다. Claude Code 함수 훅을 통한 실제 모델 전환도 CLI와 데스크톱 Code 탭에서 확인했다.

프록시의 오류·보호 규칙 로컬 검증은 `127.0.0.1` 모의 서버와 합성 토큰·프롬프트로 실행했다. 앞서 기록된 TypeSafe Jev 실호출 45건에 더해 Claude 데스크톱 관찰 훅 2건, Codex CLI 연속 시험 4건, Codex 데스크톱 `shadow`·`auto` 각 1건을 확인했다. 첫 CLI 연속 시험은 중단 전 시도 수를 기록하지 못해 총 누적 호출 수는 확정할 수 없다. 확인된 CLI 4건은 시도별 로컬 기록과 상한 4회를 적용했다. Codex 전역 모델 설정은 데스크톱 시험 중에만 임시 변경하고 원본 해시를 확인해 복원했다. 승인받은 Claude Code 작업 공간 신뢰는 이 저장소에 부여했으며, 데스크톱 시험용 프로젝트 관찰 훅 설정은 제거했다. Claude CLI의 기본 인증을 구독으로 맞추기 위해 셸 시작 파일의 API 키 자동 설정 한 줄만 백업 후 비활성화했다.

| 검증 항목 | 로컬 검증 결과 |
| --- | --- |
| HTTP 상태·본문·일반 헤더, 인증 헤더 전달 | 429·재시도 헤더·요청 ID·합성 인증값 전달 확인 |
| 연결 전용 헤더 | 양방향 `Connection`에 명시한 추가 헤더를 제거하도록 수정·확인 |
| SSE 정상 출력·중도 끊김 | 정상 출력 보존, 중도 끊김 시 클라이언트 스트림 오류와 프록시 후속 정상 응답 확인 |
| 모델 목록 중도 끊김 | 무기한 대기 문제 수정, 정제된 502 확인 |
| 클라이언트 취소·서버 종료 | 업스트림 연결 취소, 활성 SSE가 있어도 서버 종료 완료 확인 |
| 잘못된 JSON | 업스트림 호출 없이 400 반환 확인 |
| Jev 타임아웃·로그 | 모의 HTTP 타임아웃에서 기본 모델 유지, 지표에 프롬프트·키·원문 오류 없음 확인 |
| 모델 고정·전환 | `force` 도구 연속 요청 고정, 모의 `balanced → fast → balanced`, 세션 분리 확인 |
| 보호 규칙 | 짧은 후속 지시는 이전 모델 유지, 큰 문맥·명백한 비밀 문자열은 `fast` 사용 중 기준 모델로 복귀, Jev 미호출 확인 |
| 응답 모델·캐시 관찰 | 완료 SSE의 실제 모델 ID·입력/캐시/출력 토큰 기록과 원문 바이트 보존을 모의 서버로 확인. 실제 Codex 업스트림이 `Content-Type`을 생략하고 완료 뒤 연결을 닫는 경우도 처리. Jev 실패 후 `fast`에서 기준 모델로 복귀한 지표도 실제 요청 모델과 일치하도록 수정 |
| 선택적 하향 전환 보류 | `--downgrade-confidence`로 낮은 신뢰도의 하향 전환만 보류하고 상향 전환은 유지하는 정책 단위 테스트 통과 |

앱의 공개 합성 턴 연결은 확인했지만, 실제 업스트림의 오류·재시도 동작과 일반 업무의 모델 전환 품질까지 검증한 것은 아니다. 종료 처리는 [Node.js HTTP 문서](https://nodejs.org/api/http.html#servercloseallconnections)에 따라 신규 연결을 중단한 뒤 활성 연결을 닫는다.

응답 모델·캐시 관찰과 하향 전환 보류 옵션은 합성 응답과 모의 Jev로 먼저 검증했다. 상시 설치 후 공개 합성 Codex CLI 턴 1건은 실제 Jev `fast`(신뢰도 1, 입력 456토큰, 지연 547ms)에 따라 `gpt-6-luna`로 완료됐다. 이때 실제 업스트림의 `Content-Type` 생략·완료 후 연결 종료 때문에 응답 관찰 행이 빠져, 헤더 없이 SSE를 식별하고 완료 이벤트를 즉시 기록하도록 수정했다. 수정 후 짧은 공개 합성 CLI 턴에서는 Jev 호출 없이 요청·실제 응답 모델 `gpt-6-astra`가 모두 기록됐다. `observedResponses`는 완료 이벤트를 읽은 요청만 포함하므로 관찰 누락이 곧 응답 실패를 뜻하지 않는다.

이 개발 머신에서는 Claude 사용자 범위 함수 훅과 Codex 사용자 수준 공급자 설정을 활성화하고, 로컬 Codex 프록시를 로그인 시 자동 시작하는 서비스로 등록했다. 이전 `agent-auto` 가상 모델명은 제한된 시험에서 동작했지만 실제 Codex 앱 작업에서 ChatGPT 계정이 지원하지 않는 모델이라는 오류가 났다. 설정을 백업하고 최상위 모델을 실제 지원 모델인 `gpt-6-astra`로 변경했다. 프록시는 이 기준 모델 요청을 Jev 추천에 따라 라우팅한다. 이전 설정에서 Claude CLI와 데스크톱 Code 탭의 공개 합성 턴은 실제 `claude-haiku-4-5` 응답을 확인했고, Codex CLI와 데스크톱의 공개 합성 턴도 요청·실제 응답 모델 `gpt-6-luna`를 확인했다.

Jev 요청 한 번에서 모델 등급과 effort 점수를 함께 받도록 수정했다. 새 설정으로 실행한 Codex CLI 공개 합성 턴은 `fast`·`low`로 분류되어 `gpt-6-luna`에 전달됐고, 응답 관찰에서도 같은 모델을 확인했다(입력 574토큰, Jev 지연 592ms). Claude CLI 공개 합성 턴도 실제 `claude-haiku-4-5`로 완료됐다. Codex 앱을 재시작한 뒤 새 작업에서 보낸 공개 합성 턴은 `fast`·`low`로 분류되어 `gpt-6-luna`에 전달됐고, 같은 요청 ID의 응답 관찰에서 실제 응답 모델 `gpt-6-luna`를 확인했다(입력 576토큰, Jev 지연 560ms). effort는 요청에 적용된 값을 확인했으며 서버가 실제 사용한 내부 추론량은 응답에 표시되지 않는다. 각 실제 확인은 공개 예문 한 턴에 한정된다.

모델 선택 표시 개선: Codex 앱의 `model/list`는 모델 카탈로그의 정적 이름과 effort 선택지를 표시한다. `auto` 모드에서만 기존 기준 모델 `gpt-6-astra`의 표시 이름을 `Jev Auto`로 바꾸고 실제 모델 ID·지원 effort 값은 유지했다. 별도 app-server의 `model/list` 호출에서 `model=gpt-6-astra`, `displayName=Jev Auto`를 확인했다. 이는 새 가상 모델 ID를 만들지 않으며, 앱 선택 영역에 실제 턴별 응답 모델·effort를 표시하는 기능은 아니다. 로컬 `/status` 화면은 지표 파일의 요청 ID로 판정과 완료 응답을 연결해 전체 Codex 작업의 실제 응답 모델·요청 effort를 보여준다. 합성 지표를 사용한 로컬 HTTP 시험에서 표시·JSON 응답·프롬프트 미노출을 확인했고, 기존 실제 지표를 읽는 별도 로컬 서버에서도 `gpt-6-luna`·`low`가 표시되는 것을 확인했다. 앱을 재시작한 실제 선택 영역의 최종 표시 확인은 남아 있다.

Auto effort 메뉴 검토: 설치된 Codex `0.155.0-alpha.16.4`의 app-server는 `ReasoningEffort`를 문자열로 받고, 합성 카탈로그의 `auto` 선택지·기본값을 `model/list`에 반환했다. 그러나 데스크톱 앱의 실제 메뉴 코드는 별도의 고정 목록(`none`·`minimal`·`low`·`medium`·`high`·`xhigh`·`max`·`ultra`·`persistent`)으로 선택지를 필터링해 `auto`를 제외한다. 따라서 app-server 응답만으로 네이티브 메뉴 추가를 검증할 수 없다. 시험용 `auto` effort 카탈로그와 요청 변환 구현은 되돌렸으며, 전역 effort 설정은 변경하지 않았다. Jev Auto의 모델·effort 자동 선택과 상태 화면은 기존대로 유지한다. 이 검토에는 유료 모델 호출을 사용하지 않았다.

기존 작업의 연결 확인: 설정 변경 전에 생성한 데스크톱 작업은 Jev Auto를 선택한 뒤에도 `thread/read`의 `modelProvider`가 `openai`였고, 같은 작업 디렉터리의 `config/read` 결과는 새 작업용 `agent_router`였다. 라우터 지표와 `/status.json`의 마지막 시각도 새 메시지 뒤 갱신되지 않았다. 모델 목록의 표시 이름은 기존 작업의 공급자 연결을 바꾸지 않는다. 기본 `openai` 공급자의 주소를 설정으로 덮어쓰는 모의 시험은 Codex가 내장 공급자 ID 재정의를 금지해 요청 전 단계에서 거절됐다. 전역 설정은 변경하지 않았고, 상태 화면에 화면 갱신 시각·마지막 라우터 기록·새 작업 필요 조건을 추가했다. 이 연결 진단에는 유료 모델 호출을 사용하지 않았다.

## 2. Jev 추천 품질

`fixtures/routing-cases.json`의 합성 사례를 시작점으로, 실제 사용에 가까운 한국어 턴 최소 30개를 사람이 먼저 독립적으로 등급 판정한다. `amr evaluate`의 결과와 비교한다.

초기 등급 부여 사례는 10개다. 추가로 [판정 후보 30개](../fixtures/routing-candidates.json)를 준비했지만 `expectedTier`는 모두 비워 두었다. 이 후보는 아직 사람이 독립 판정한 자료가 아니므로 정확도 목표의 근거로 사용할 수 없다.

검토자가 추천 결과를 보기 전에 후보 파일을 `.local/routing-reviewed.json`으로 복사하고, 각 `expectedTier`를 `fast`·`balanced`·`strong` 중 하나로 독립 판정한다. 수정 중인 파일에는 원문 프롬프트가 포함되므로 외부에 공유하지 않는다. 30개 모두 채우고 다시 검토한 후 `node dist/cli.js evaluate .local/routing-reviewed.json --max-calls 30`으로 평가한다. 이 명령은 **유료 TypeSafe API를 최대 30회 호출**하므로 사례·비용·키 주입 범위를 확인받기 전에는 실행하지 않는다. 빈 라벨, 중복 ID, 잘못된 문맥 토큰 수, 상한 초과는 첫 요청 전에 거절한다.

평가 출력은 `accuracy=정답/전체 사례`(API 실패는 오답), `classifiedAccuracy=정답/분류 성공`, `errorRate=실패/전체`, `falseFastRate=balanced·strong을 fast로 분류한 건수/전체 balanced·strong 사례`, `underRoutingRate=예상보다 낮은 등급을 선택한 건수/전체 balanced·strong 사례`, 전체 Jev 호출 지연 p95와 Jev 응답 모델 버전을 보여준다. 하향 분류에는 `strong → balanced`도 포함한다. 첫 기준의 정확도 90%와 위험한 `fast` 오분류 5%를 이 분모로 판단한다. 예상 등급이 `fast`뿐이면 두 하향 분류 비율은 `null`이다. `jev-latest`는 새 버전이 나오면 바뀔 수 있으므로 응답 버전을 함께 읽는다.

초기 통과 기준: 전체 정확도 90% 이상, `balanced`/`strong` 사례를 `fast`로 잘못 분류한 비율 5% 이하, Jev 호출 p95 1.2초 이하. 이 수치는 사람이 독립 판정한 30건 이상의 출시 전 검증용 목표다. 기존 합성 10건의 예비평가만으로 통과 판정하지 않는다. 실패하면 기준·문맥 요약·모델 매핑을 조정하고 사례를 다시 평가한다.

2026-09-25 연결 확인: 사용자 승인 범위인 `.local/jev-smoke.json` 1건을 `--max-calls 1`로 실행했다. 공개 합성 맞춤법 요청을 예상대로 `fast`로 분류했고, 응답 모델은 `jev-1.13.0`, 신뢰도는 `1`, 입력 467토큰, 호출 지연 572ms였다. 공개 단가로 계산한 Jev 입력 비용 추정치는 약 `$0.0000196`이며 실제 청구 금액은 확인하지 않았다. 이 1건은 키 주입·API 스키마·응답 파싱이 동작한다는 증거일 뿐, 30개 평가의 정확도·위험 오분류율·지연 기준을 통과했다는 뜻은 아니다.

2026-09-25 예비평가: 이미 예상 등급이 적힌 `fixtures/routing-cases.json`의 공개 합성 10건을 `--max-calls 10`으로 한 번 실행했다. `jev-1.13.0`에서 분류 성공 10/10, 예상 등급과 일치 10/10, 오류 0, `balanced`·`strong` 7건 중 `fast` 오분류 0, Jev 지연 p95 594ms, 입력 4,775토큰이었다. 공개 단가 기준 입력 비용 추정치는 약 `$0.0002006`이며 실제 청구 금액은 확인하지 않았다. 신뢰도 0.8 미만은 2건이어서 현재 자동 전환 정책에서는 기존 모델을 유지한다. 이 10건은 독립 인적 판정 자료가 아니며 실제 작업 분포를 대표하지 않으므로 30건 검증을 대체하지 않는다.

## 3. 관찰 모드

Codex CLI와 앱, Claude Code CLI와 데스크톱 Code 탭에서 `shadow` 로그를 각각 확인한다. 프롬프트 저장 없이 선택 분포, 오류율, Jev 토큰·비용, 지연을 집계한다. Jev의 한국어 판정이 불안정하거나 24,000토큰 이상 문맥이 자주 발생하면 자동 전환으로 넘어가지 않는다.

2026-09-25 설치 확인: Claude 데스크톱 앱은 처음에 1.46388.4였고 공식 앱 업데이트 후 2.9939.2가 됐다. 터미널 Claude Code는 2.1.282이고 사용자 설정의 표준 훅 이벤트는 비어 있다. 처음에는 API 키를 제거한 합성 한 턴도 401을 반환했다. 사용자가 Claude CLI에 재로그인한 뒤 같은 비대화형 요청이 완료되어 401이 재현되지 않았다. 이어 임시 `--settings`로 `UserPromptSubmit` 훅을 붙인 실제 Claude CLI 턴을 완료했다. 짧은 입력은 `kept`·`short-follow-up`으로 기록되어 Jev를 호출하지 않았다. 이후 로그인 키체인을 훅 자식에서 직접 읽도록 하여 별도의 합성 맞춤법 턴에서 Jev `fast` 추천을 1회 기록했다(입력 465토큰, 지연 577ms). TypeSafe 키와 프롬프트는 지표에 기록하지 않았고 임시 훅은 제거했다. [공식 표준 훅 문서](https://code.claude.com/docs/en/hooks)에 따르면 `UserPromptSubmit`은 프롬프트 차단·문맥 추가를 지원하며 비동기 명령 훅은 동작을 제어할 수 없다. 따라서 이 표준 훅은 추천 관찰 전용이다. Codex CLI `shadow` 실호출은 공개 합성 요약 요청 한 턴을 `gpt-6-sol` 그대로 완료하고 Jev `fast` 추천만 1회 기록했다(입력 469토큰, 지연 588ms). 프록시에 주입한 TypeSafe 키를 Codex 자식 프로세스 환경에서는 제거하도록 수정했고, 합성 키를 이용한 실제 자식 실행에서도 이를 확인했다. 지표에는 프롬프트가 없었다.

두 번째 데스크톱 `shadow` 시험에서는 키체인을 읽는 서버와 원래의 `gpt-6-astra` 기준 모델을 사용했다. 실제 앱의 새 입력은 정적 도구 스키마·개발자 지시를 문맥에 포함해 약 32,026토큰으로 과대 추정되어 `large-context` 보호 규칙으로 Jev를 건너뛰었다. 정적 항목은 제외하고 사용자·도구 대화 내용은 유지하도록 추정기를 수정해 45개 테스트와 타입 검사를 통과했다. 다음 앱 시험에서 새 공개 합성 사용자 턴은 Jev `fast`(신뢰도 1, 입력 463토큰, 지연 626ms)로 분류됐고 `shadow`는 기존 `gpt-6-astra`를 유지했다. 로컬 세션 기록에서 사용자 입력·최종 응답·작업 완료를 확인했다. 앱 화면 자동 제어는 안전 제한으로 사용할 수 없어 사용자가 앱 재시작과 입력을 직접 수행했다.

로그인 키체인 옵션을 Codex CLI·로컬 서버·평가 명령에도 연결했다. 입력 사례와 호출 상한을 검사한 뒤에만 평가용 키를 읽고, 키체인 항목이 없으면 유료 요청 전에 중단한다. 실제 로그인 키체인으로 `shadow` 서버를 시작해 `/health` 응답을 확인하고 종료했으며 TypeSafe 요청은 보내지 않았다. 자동화 테스트는 합성 항목만 사용했다.

## 4. 제한적 자동 전환

Codex에서는 `auto`를 켜고 작은 실제 작업을 순서대로 확인한다: `balanced → fast → balanced`, 수동 모델 우선, 짧은 후속 지시, 도구 연속 요청, 이미지 턴. 품질 저하나 전환 실패가 보이면 즉시 `shadow` 또는 `pass`로 되돌린다. Claude Code는 별도의 초기 접근 함수 훅으로 합성 턴의 실제 모델 전환을 시험한다.

2026-09-25 격리된 합성 시험: CLI `auto`를 각 한 턴의 임시 세션에서 실행했다. 맞춤법 요청은 Jev `fast`(신뢰도 1)로 `gpt-6-luna`에 전환해 완료했다. 결제 중복 청구 대응 요청은 Jev `balanced`(신뢰도 0.72)로 분류됐고 신뢰도 보호 규칙에 따라 기존 `gpt-6-sol`에서 완료했다. API 게이트웨이 방식은 별도 요금·자격 증명 범위로 분리한다.

## 추가 평가 재실행 시 확인할 범위

1. 평가 출력 보완과 후보 30개 준비, 로그인 키체인을 통한 키 주입, 1건 연결 확인과 10건·30건 예비평가는 완료했다. 사용자는 인적 판정 단계를 생략하고 제한 시험을 계속하기로 했으므로, 후보 30개는 여전히 인적 검증 자료가 아니다. 키 값은 대화로 받지 않으며 [로컬 비밀 주입 안내](local-secrets.md)를 따른다.
2. 대량의 유료 Jev 평가를 다시 실행할 때는 합성 사례 파일, 호출 상한(사례당 1회, 자동 재시도 없음), 전송할 프롬프트 최대 1,600자, 적용 단가와 비용 범위를 먼저 명시한다. Claude 함수 훅의 일상 사용도 사용자 턴마다 유료 Jev 요청을 보낼 수 있다.
3. 전역 설정 변경은 대상 파일과 변경 내용, 백업·복원 방법, 새 세션에 미치는 영향을 기록한다.

완료한 유료 API 연결 확인은 `.local/jev-smoke.json`의 기존 합성 맞춤법 사례 1개를 `--max-calls 1`로 실행했다. 전송 내용은 `jev-latest` 분류 질문, 공개 합성 프롬프트 `다음 한국어 문장의 맞춤법과 띄어쓰기만 수정해줘: 오늘은 날씨가 참 좋내요.`, 문맥 토큰 추정치 `200`, 현재 모델명 `gpt-6-sol`이다. 자동 재시도나 두 번째 요청은 없었다. [공개 입력 토큰 단가](https://docs.typesafe.ai/models)는 백만 토큰당 $0.042이며, 실제 청구액은 응답의 사용량과 계정 요금 조건에 따른다.

## 기록 원칙

실제 사용자 프롬프트, 인증 토큰, 서버 응답 전문은 저장하지 않는다. 사례 평가는 공개·합성 프롬프트를 사용한다. 회사 자료를 Jev로 보내려면 회사의 외부 서비스 사용 정책과 데이터 처리 조건을 먼저 확인한다.

## 응답 마지막 라우팅 요약

자동 라우팅의 정상 최종 답변에 `모델: … · 요청 effort: …`를 표시한다. 모델은 API 응답 메타데이터를 사용하며, effort는 요청값이다. 서버 내부 추론량으로 해석하지 않는다. Codex는 텍스트 델타를 바로 전달하고 종료 이벤트만 완료 메타데이터까지 보류한 뒤 델타·완료 텍스트·완료 항목을 같은 내용으로 갱신한다. Claude는 공식 `turn.complete` 훅의 하단 요약 표시를 사용하며 대화 원문은 바꾸지 않는다.

도구 호출·중간 commentary·중단/오류 응답에는 표시하지 않는다. Codex의 구조화 출력·제목 생성·수동 모델·pass/shadow 모드는 보존한다. 미지원 형식·압축·4MiB를 초과하는 보류 데이터는 원문을 전달한다. Claude에서 `AMR_RESPONSE_FOOTER=0`, Codex에서 `--response-footer off`로 끌 수 있다.

합성 스트림의 한 바이트 청크·한글/이모지·CRLF·완료 이벤트 순서·실제 모델과 요청 모델 불일치·JSON 응답·관찰 지표 보존을 검증했다. Claude 플러그인 strict 검증과 완료/중단/하위 에이전트/옵트아웃 훅 테스트를 통과했다. 실제 데스크톱 UI의 새 버전 표시는 별도 적용 후 확인 대상이다.

추가 연결 확인: 설치된 Codex CLI `0.155.0-alpha.16.4`에 로컬 합성 Responses 서버와 합성 Jev 판정을 연결했다. CLI의 `item.completed` 최종 메시지에 `Synthetic footer check.\n\n— 모델: gpt-6-luna · 요청 effort: low`가 정확히 한 번 포함됐고 `turn.completed`·종료 코드 0을 확인했다. 실제 TypeSafe·OpenAI 모델 요청은 사용하지 않았고 전역 공급자 설정은 변경하지 않았다. Claude는 `turn.complete` 공식 타입 계약과 플러그인 strict 검사·합성 훅 테스트로 검증했으며 실제 UI 확인은 새 세션 적용 후 진행한다.

## 간편 설치 도구와 마켓플레이스

`npm run setup [-- codex|claude]`, `npm run doctor`, `npm run disable [-- codex|claude]`를 추가했다. macOS의 Codex LaunchAgent와 두 클라이언트의 사용자 설정을 백업·등록·진단·해제하며, 이전 수동 설치도 등록한다. 기존 수동 라우터를 등록했다가 해제하면 Codex는 `openai` 공급자로, Claude 자동 라우팅은 꺼짐으로 복귀한다. 새로운 기본 경로 설치에서는 원래 설정값으로 복원한다.

임시 사용자 디렉터리에서 관련 없는 설정 보존, 설치 반복, 해제, 마켓플레이스 중복 방지, 다른 플러그인 경로 충돌, 포트 충돌, 서버 시작 실패 복원, XML 경로 이스케이프, 사용자 지정 설정 경로 보호를 검증했다. 서버 제어와 준비 응답은 이 테스트에서 모의 실행했으며 실제 LaunchAgent 변경 검증을 대신하지 않는다. 실제 사용자 환경의 읽기 전용 진단에서는 Claude 로컬 플러그인·자동 설정, Codex 공급자·기존 서비스·구버전 서버 응답을 확인했다. 사용자 설정과 실행 중인 서비스는 아직 설치 도구로 변경하지 않았다.

Claude 마켓플레이스 목록과 플러그인 strict 검사를 통과했다. 마켓플레이스 등록은 이 버전을 원격에 게시한 후 사용할 수 있다. Codex 마켓플레이스 패키지는 제공하지 않으며 공식 공급자 설정과 로컬 서비스 실행을 설치 도구로 묶었다.

이번 변경의 최종 자동 검증: 테스트 84개, TypeScript 타입 검사, Claude 플러그인·마켓플레이스 strict 검증, `git diff --check` 통과. 로컬 모델 모의 서버를 이용한 Codex CLI 완료 확인을 포함하며 실제 Claude 데스크톱 UI나 새 LaunchAgent의 실운영 검증은 포함하지 않는다.

## 실제 Codex 완료 이벤트의 빈 output 대응

사용자 채팅에서 요약이 표시되지 않아 실제 서버 이벤트의 구조만 관찰했다. 실제 ChatGPT Codex 백엔드는 본문을 `response.output_item.done`에 포함하지만 `response.completed.response.output`은 빈 배열로 보냈다. 기존 합성 테스트는 마지막 output에도 본문이 있다고 가정해 이 경우를 놓쳤다. 완료 메타데이터의 실제 모델과 앞선 완료 항목을 결합하도록 수정하고, reasoning 때문에 최종 항목의 output_index가 0이 아닌 경우·이전 도구 호출·commentary 제외 회귀 테스트를 추가했다.

사용자 승인 후 설치 도구로 기존 설정을 백업하고 실제 LaunchAgent를 재시작했다. 수정 후 실행 중인 프록시를 통해 설치된 Codex CLI에서 공개 합성 `Say OK.` 요청 1건을 완료했고, 최종 메시지 `OK\n\n— 모델: gpt-6-astra · 요청 effort: xhigh`와 표시 횟수 1, 종료 코드 0을 확인했다. 완료 이벤트의 output은 여전히 빈 배열로 보존됐다. 진단 요청 1건과 수정 후 확인 1건은 각각 실제 Codex 구독 요청이며 짧은 입력 보호 규칙으로 Jev 분류를 호출하지 않았다. 테스트 86개와 타입 검사도 통과했다. 데스크톱 화면의 최종 렌더링은 사용자 채팅에서 확인 대상이다.
